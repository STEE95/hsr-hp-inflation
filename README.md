# 星穹铁道 · 终局玩法血量膨胀分析

追踪崩坏：星穹铁道四种终局玩法（混沌回忆 / 虚构叙事 / 末日幻影 / 异相仲裁）各正式服版本最高难度的血量，提供膨胀曲线、环比膨胀率、相对基准倍数、指数/线性拟合、拐点检测与膨胀加速度分析。

数据来源：[nanoka.cc](https://hsr.nanoka.cc/maze/)（静态 JSON，仅抓取正式服 live 版本，自动排除测试服预载数据）。

## 目录结构

```
hsr-hp-inflation/
├── index.html                     # 前端页面（ECharts + 数学分析 + 高清导出）
├── data/
│   ├── health_data.json           # 爬虫输出（结构化数据）
│   ├── health_data.js             # 同内容 JS 版本（页面加载用）
│   └── overrides.json             # 手动修正覆盖层（与自动抓取分离）
├── scripts/
│   ├── scraper.py                 # 抓取 + 血量计算 + 安全写入
│   └── validate.py                # 数据完整性校验（防止坏数据上线）
└── .github/workflows/scrape.yml   # 每周定时抓取（GitHub Actions）
```

## 血量口径

| 玩法 | 口径 |
|---|---|
| 混沌回忆 | 最高层（第12层）两路 + 星启第三路的怪物血量总和 |
| 末日幻影 | 难度04 两路 + 星启第三路（Boss 按多阶段血量之和） |
| 虚构叙事 | 第一波 Σ小怪（虚构集合体不计入）+ 第二三波「40%×BOSS + Σ小怪实际数量」 |
| 异相仲裁 | 三骑士总和、王棋、绝境王棋 三个值独立输出 |

四种玩法统一使用**游戏版本号**（如 4.5）作为横轴标识，可直接横向对照。

单怪血量公式：`HP = HPBase × HPModifyRatio × 精英组HPRatio × 等级HPRatio × Σ(阶段倍率)`

### 正式服版本判定与版本号对齐

**数据包**：首页 `data-url` 指向的就是官方最新包（如 `4.5.54`），其中已包含正式服开放的赛季；
是否正式服由 `maze.json` 中的 `live_begin` 字段判定（如 4.5 为正式服、4.6 尚未上线）。

**版本号对齐**：末日幻影 / 虚构叙事上游只提供赛季号（`s3020` / `s2026`），无法直接与混沌回忆对照。
爬虫按以下锚点统一回填为游戏版本号：

| 依据 | 内容 |
|---|---|
| 官方 4.3 更新说明 | 当期三玩法为「末日·遗忘冽风 / 虚构·借虚成真 / 混沌·学院怪谈」，与本项目 s3018 / s2024 / 1033 逐一对应 |
| 星启模式 | 自 4.3 起上线，三者恰在同期首次出现星启关卡 |
| 更新节奏 | 4.x 期间各玩法均为一版本一期 |

由此 `s3018 = 4.3`、`s2024 = 4.3`，并按同一步长前后展开；最新一期（`s3020` / `s2026`）即 **4.5**，
与混沌回忆同一标尺，可直接横向对照。

### 数据安全机制

**这是整个自动化里最重要的设计。** 上游 `nanoka.cc` 一旦改版或临时抽风，各抓取函数会返回空列表。
如果没有防护，脚本会「成功」写出一份全空数据并提交，网站上所有曲线**静默消失**，而且要等到下次有人访问才会发现。

因此抓取流程被拆成两道关：

| 环节 | 作用 |
|---|---|
| 写入临时文件 | 不直接碰正式数据文件，失败时正式数据分毫不动 |
| `validate.py` 校验 | 六类检查全过才允许替换；不过则以退出码 1 失败 |

校验项：

1. **结构完整** —— 四种玩法齐备，且 data 均非空
2. **数值合法** —— 血量均为正数、无 `None`、不超过 1 万亿上限
3. **版本号格式** —— 形如 `4.5`，不允许出现 `s3020` / `2026` 这类季节号
4. **时间顺序** —— 版本号严格递增、无重复
5. **最新版本** —— 末位应与 `meta.liveVersion` 一致，确保没混进未上线赛季
6. **收缩检查** —— 数据点不得比上一版减少超过 10%（正式服赛季只累积不回退）

任何一项不过，正式数据文件保持不变，网站不受影响。工作流会标红，GitHub 会给你发邮件。

### 需要人工处理的情况

**情况一：Actions 页面出现红色 ❌**

先点进去看失败在哪一步：

| 失败位置 | 含义 | 处理 |
|---|---|---|
| 「运行爬虫」且提示某玩法为空 | 上游改版或临时限流 | 本地跑 `python scripts/scraper.py /tmp/probe.json` 复现；若同样为空，对照站点结构调整解析逻辑 |
| 「运行爬虫」且提示数据点减少 | 这次抓取不完整 | 多半是上游临时问题，直接 **Re-run** 一次；连续失败再排查 |
| 「运行爬虫」日志里有 traceback | 代码异常 | 按报错行号排查 |
| 「提交数据变更」失败 | 权限问题 | Settings → Actions → General → Workflow permissions 选 **Read and write** |

**情况二：上游数据结构变了**

这是第三方数据源，长期使用中**一定会遇到**。届时表现为抓取返回空或数值明显不对。
处理步骤：

```bash
# 1. 复现
python scripts/scraper.py /tmp/probe.json

# 2. 观察上游当前结构
curl -s "https://hsr.nanoka.cc/maze/" | grep -o '/hsr/[0-9.]*/' | head -1

# 3. 对照调整 scripts/scraper.py 中的解析逻辑
#    （血量公式、字段名、JSON 路径都集中在文件上半部分）

# 4. 本地验证通过后再手动触发一次 workflow
```

**情况三：数据有个别看错，想手工修正**

不要直接改 `health_data.json`——下次抓取会被覆盖。改用 `data/overrides.json` 覆盖层：

```json
{
  "chaosMemory": {
    "4.5": { "hp": 87203907 }
  }
}
```

格式为「玩法 → 版本号 → 要覆盖的字段」。爬虫每次抓取后会重新应用这些修正，因此能长期保留。

**情况四：想手动立刻更新一次**

仓库 Actions 页面 → 「每周抓取血量数据」→ **Run workflow**。

**情况五：线上数据看起来是旧的**

1. 先看页面右上角「更新于」时间——若已是新时间，说明只是浏览器缓存，强制刷新（Ctrl/Cmd + Shift + R）即可
2. 若时间也是旧的，去 Actions 看最近一次运行是否成功
3. 若 Actions 成功但线上仍旧，去 Cloudflare Pages 看最近一次部署状态

> 缓存问题已由脚本自动处理：每次抓取会把 `index.html` 里
> `health_data.js?v=YYYYMMDD` 的查询串更新为当天日期，
> 访问者与 CDN 都会因此重新拉取数据，不需要人工记得改。

### 什么情况下这个站点会失效

诚实地说明风险，便于早做打算：

| 风险 | 影响 | 缓解 |
|---|---|---|
| `nanoka.cc` 停止运营或改版 | 无法继续抓取新数据 | 已有数据仍可展示；需寻找替代数据源并改写 scraper |
| 站点前端结构大改 | 抓取逻辑失效 | 按「情况二」调整；`validate.py` 会先一步拦截坏数据 |
| GitHub Actions 免费额度 | 本任务每月仅消耗约 4 次运行，远低于免费额度 | 基本无需担心 |
| 游戏本身停更 | 不再有新版本数据 | 数据自然定格，站点仍可用 |

**核心设计原则：数据文件的格式与展示逻辑是解耦的。** 即使抓取彻底失效，只要 `health_data.json`
还在，网站就能正常展示历史数据。最坏的情况是「不再更新」，而不是「变成空白页」。

## 故障排查

### 本地自检命令

怀疑哪里不对时，按顺序跑这三条，基本能定位问题：

```bash
# 1. 只抓取、不写入，看各玩法抓到多少条
python scripts/scraper.py /tmp/probe.json

# 2. 单独校验现有数据是否健康
python scripts/validate.py data/health_data.json

# 3. 对比新抓的与现有的，校验是否会通过
python scripts/validate.py /tmp/probe.json data/health_data.json
```

### 常见问题对照

| 现象 | 大概率原因 | 处理 |
|---|---|---|
| 曲线全部消失 | 数据被空数据覆盖（旧版才会发生） | 用 `git log data/health_data.json` 找到上次正常版本，`git revert` 后排查爬虫 |
| 某玩法曲线明显偏低/偏高 | 血量倍率链算错 | 检查 `scripts/scraper.py` 中该玩法的倍率相乘逻辑 |
| 版本号显示成 `s` 开头 | 前端退回显示 seasonId | 说明数据里 `version` 为空，跑一下校验；正常数据不该出现 |
| Y 轴被某个关卡撑大后不缩回 | 轴范围残留 | 已在代码中修复（`yAxis.min/max` 显式设 `null`），若复现检查是否被改回 |
| Actions 成功但线上没变 | Cloudflare 部署未触发 | 去 Pages 看 Deployments 列表；确认仓库已 Connect to Git |
| 线上是旧数据但 Actions 已成功 | 缓存 | 强制刷新；检查 `index.html` 里 `?v=` 是否为最新日期 |

## 切换过渡动画

主图在**切换玩法**（混沌回忆 / 虚构叙事 / 末日幻影 / 异相仲裁）与**切换子指标**
（三骑士总和 / 王棋 / 绝境王棋）时都会播放过渡动画。两类切换的机制不同：

### 玩法切换 → ECharts 原生形变动画

四种玩法的总血量曲线**共用同一个 series id（`main_total`）**。切换玩法时 ECharts
把它认作"同一条曲线的数据更新"，于是播放原生形变动画：曲线始终可见，形状与位置
平滑移动，数据点符号跟着走。

> 关键：id 必须固定。早期用 `mode.key + "_total"` 作为 id，切换时 ECharts 视为两条
> 不相干的曲线（旧的删除、新的凭空出现），只能得到瞬变，毫无动画可言。

曲线条数不同（1 条 ↔ 3 条）时用 `replaceMerge: ["series"]` 重建集合。

### 子指标切换 → 显式补间透明度

异相仲裁三条曲线的**几何完全相同**（同一组 x 轴、同一批数据），切换只是高亮对象变了。
这种情况下 ECharts 的形变动画帮不上忙 —— 没有"位置"可供补间，动画在视觉上等于没有。
因此这里显式补间不透明度与线宽（高亮 `1` / 线宽 `3.2`，非高亮 `0.42` / `1.8`），
用 `setInterval` 每 16ms 算一帧，时长 320ms。曲线全程可见，只是亮暗互换。

> 非高亮的透明度曾是 `0.22`，实测在深色底上几乎看不见（像素数 679 vs 高亮曲线 70470，
> 差两个数量级），另外两条参照曲线等于白画。改成 `0.42` 后主次依然分明，
> 但三条都读得出来。

### 三个曾经踩过的坑

1. **不要用"旧曲线淡出 + 新曲线淡入"做交叉过渡。** 两条半透明曲线叠在同一位置，
   中间时刻两边都接近透明，曲线会"消失一下" —— 实测 t=200ms 时曲线像素降为 0，
   观感比原生形变生硬得多。
2. **过渡起点必须在普通渲染后同步记录。** 子指标过渡的起点存在 `currentStyle` 里，
   如果普通渲染后不更新它，首次进入某玩法时起点为空、插值退化，动画等于没播。
3. **自定义图例必须自己绑点击事件。** `renderLegend()` 用 `innerHTML` 重建图例后，
   新生成的 DOM 不会继承任何监听器。曾出现"图例纯属装饰、点了没反应"，
   导致子指标只能靠上方 Tab 切换、过渡动画完全没机会播放。

> 其余已知陷阱：`animationThreshold` 不能设为 `0`（会被判定为 falsy，动画整体跳过）；
> `replaceMerge` 与 `notMerge` 都按 id 对齐，series 条数变化会留下 `null` 空洞。

## Y 轴自适应

**每个关卡各用各的 Y 轴刻度**，互不影响：混沌回忆 ≈ 1 亿、虚构叙事 ≈ 3 亿、
末日幻影 ≈ 1.5 亿、异相仲裁 ≈ 2.5 亿。异相仲裁的三条曲线同处一张图，
共用一个按最大值（三骑士总和）确定的轴，以便三条主线互相可比。

实现上有两点必须注意：

1. **`yAxis.min` / `yAxis.max` 要显式写成 `null`，不能省略。** ECharts 的 `setOption`
   是合并语义：一旦某个关卡写过固定的 min/max，切到别的关卡时不显式覆盖，旧范围就会
   一直残留。曾经的 bug 就是"看过一次最高血量的关卡后，所有关卡的 Y 轴都被撑大、
   不再自适应"。
2. **早先那套"共轴 + 写死范围"的代码已整体删除**（`setAxisScale` / `hpMax` / `unionMax`
   以及 `MODES` 里的 `subSharesAxis` 标记）。它本意是避免切换时坐标轴跳动，
   实际代价是牺牲了各关卡的自适应，得不偿失。

另外 `grid.left` 设为 `56`：刻度经 `fmt()` 会输出「5000.00 万」「2.50 亿」这类较长文本，
`left` 太小（如 `10`）时标签会紧贴卡片边缘甚至被裁掉。
